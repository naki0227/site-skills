# 全タイプ共通の基礎（13サイトの横断）

ここに置くのは、解剖した13サイト（`compare.md` の列）のうち**2つ以上で確かめたこと**と、そこから外れるときの線引きだけ。1サイトだけの型は `types/` に置く（以前ここにあったガールスカウト100周年の型は `types/pop.md` に移した）。

## 1. 作る前に決める表
書き始める前に、次の2つを CSS の先頭に書く（13サイトとも、色と書体の語彙を少数のトークンに絞っている。数は `compare.md`）。
- **色の役割**：地・文字・補助の文字・罫（使うなら）・アクセント1色・状態の色。有彩色を**どこに持たせるか**を1行で書く（下の2）。
- **書体の役割**：見出し・本文・数字やコード。書体は1〜2つ（13サイト中、見出しと本文で書体を分けるのは とらや〔明朝＋ゴシック〕・びっくりドンキー・ガールスカウトなど少数。Linear・ほぼ日・星野リゾート・teamLab は1書体）。

## 2. 色：UI は絞り、色は「内容」に持たせる
- 13サイト中7つ（とらや・teenage engineering・ほぼ日・Apple・Linear・星野リゾート・teamLab）は、UI を白・黒・灰と1色に絞り、色は写真・記事・章の地に持たせている（`rules.md` 1・9・13・15）。
- 多色をセクションごとに使い分けるのは ガールスカウト（`types/pop.md`）だけ。スプラトゥーン3 は多色だが、CSS には白黒しか出ず色は画像が持つ。
- 本文の文字色は純黒にしない（`#111` とらや、`#1d1d1f` Apple、`#1a1a1a` 星野リゾート、`#221815` ガールスカウト）。ただし本文を薄い灰にはしない：地との比は 7:1 以上を目安にし、灰は補足の文字だけ（teamLab の補助 `#999` は黒地で 6.7:1）。

## 3. 文字：対比は大きく、本文は小さくしない
- 大きさは「極端な対比」（`rules.md` 2）。中くらいの大きさを何段も並べない。とらやは6段、teenage engineering は5段。
- **本文は16px以上**（Oatly の本文 16px・行間1.3。Linear は15px で、それより下の見本は無い）。site-skills の使用例は本文の中央値が12px、13px未満が57%で、いちばんAIっぽく見えた原因の1つだった（2026-10-26 の計測）。taste-skill の247サイト調査でも本文の中央値は16px。注記・キャプションも13px未満にしない。
- 字間：とらや・teenage engineering・ほぼ日は字間を触らない。Linear は大きいほど詰める（−.022em）。和文の字間を .1em 以上に広げるのはガールスカウトだけ。広げるのは `types/pop.md` を選んだときに限る。
- 英字の小見出し（見出しの上の小さな英字ラベル）を全セクションに付けるのはガールスカウトだけ。ほかの雰囲気では、手本が使っているときだけ使う。

## 4. 線と箱：罫は1つの値に決め、箱は飾りに使わない
- 罫・縁を使うサイトは値を1つに決めている：とらや `#ccc`、Oatly 1px の黒＋2px の硬い影、teamLab 白12%、Linear 白の 5 / 8 / 12 / 15%（`rules.md` 12・14）。
- 実サイトのトップで枠線を持つ要素は 7〜27個だった。site-skills の使用例は 75〜167個で、四辺を囲む箱を「区切り」に使ったことがAIっぽさの原因になった（2026-10-26 の計測）。面の区別は、余白か、地の色の1段の差でつける。囲むのは、表・入力欄・押せるカードのように、囲むことに意味があるものだけ。

## 5. 動き：足すもの、止まるもの
- 常に動く主役は1つ（`rules.md` 4）。イージングは1〜2種類、時間は3段階（`rules.md` 3）。
- 動きなしで完成している最初の画面を先に作り、動きは reduced-motion でも saveData でもない環境にだけ足す（`rules.md` 10、Apple）。登場は1回きり。
- ホバーは `@media (hover:hover) and (pointer:fine)` の中に閉じる（`rules.md` 7、とらや）。
- 動かすのは transform と opacity だけ。スクロールで起きることは IntersectionObserver で拾う。

## 6. 「パケット」を生かす

### 6-1. 軽さ（通信量）— リファレンスの弱点を超える

実測：トップページだけで **約17.5MB・158リクエスト**（JPEG 14.4MB、PNG 2.6MB、JS 573KB）。
スマホのパケットには重い。同じ見た目をこの数分の1で作るのがこちらの基準:

- 目安：**ファーストビュー 500KB以内、ページ全体 2MB以内**。
- 画像は AVIF/WebP＋`srcset`/`sizes`＋`loading="lazy"`。ヒーローの1枚目だけ `fetchpriority="high"`。
- カルーセルの2枚目以降は表示直前に読む。
- 装飾は画像でなく SVG / CSS / Canvas で描く（リファレンスも紙吹雪の形はSVG data URI）。
- 紙吹雪程度なら WebGL ライブラリ不要。Canvas 2D で20粒、数KBで足りる。
- `navigator.connection.saveData` が true ならアンビエントアニメと自動再生を止める。
- ローダーは「本当に読み込む物がある時だけ」。初回のみ・最大1.5秒。

### 6-2. モチーフとしてのパケット

「データの小包が届く」をデザインの比喩に使う。紙吹雪の代わりに:
- 背景のアンビエント：ノード間の線を小さな四角（パケット）が流れる。
- ローダー：`受信 37 / 100 packets` のようにカウント。
- スクロール表示：要素が「届いた」ように小さくスナップして着地する。
- 数字の強調：転送量・件数などの実数をカウントアップ。
通信・IT・物流・SaaS など「つながる」題材と相性が良い。題材に合わないときは無理に使わない。

### 6-3. パケット表現の型（Stripeの実績セクションより）
線を先に引いておき、明るい点を周期的（例：9秒）に流す。出発タイミングを線ごとにずらす（stagger）。中央ノード＋周辺ノードの連携図に粒を流せばデータフローになる。ライブカウンタを添えると「今も通信している」感覚が出る。
